Refactoring with AI: Safe, Systematic Code Improvement Without Breaking What WorksRefactoring com IA: Melhoria de Código Segura e Sistemática Sem Quebrar o que Funciona

June 2025 15 min read15 min de leitura Jefferson Valandro
Refactoring AI code quality clean code technical debt

Refactoring is one of the most undervalued engineering disciplines. The definition is precise: changing the internal structure of code without changing its external behavior. Not rewriting. Not adding features. Not fixing bugs. Restructuring — making the next change cheaper without breaking what works today.Refactoring é uma das disciplinas de engenharia mais subestimadas. A definição é precisa: mudar a estrutura interna do código sem mudar seu comportamento externo. Não reescrever. Não adicionar features. Não corrigir bugs. Reestruturar — tornando a próxima mudança mais barata sem quebrar o que funciona hoje.

AI changes refactoring in two important ways. First, it can scan existing code and identify smells faster and more consistently than manual review. Second, it can apply well-known refactoring techniques — Extract Method, Introduce Parameter Object, Replace Conditional with Polymorphism — in seconds, producing the refactored version alongside an explanation of why the change improves the code. The risk is also real: AI can introduce subtle behavior changes while claiming to preserve behavior. The discipline is knowing how to use it safely.A IA muda o refactoring de duas formas importantes. Primeiro, ela pode escanear código existente e identificar smells mais rápido e de forma mais consistente que revisão manual. Segundo, ela pode aplicar técnicas de refactoring conhecidas — Extract Method, Introduce Parameter Object, Replace Conditional with Polymorphism — em segundos, produzindo a versão refatorada junto com uma explicação de por que a mudança melhora o código. O risco também é real: a IA pode introduzir mudanças sutis de comportamento alegando preservar o comportamento. A disciplina é saber como usá-la com segurança.

The Safe Refactoring WorkflowO Workflow de Refactoring Seguro

Refactoring without tests is not refactoring — it's gambling. Before asking AI to refactor anything, establish the safety net:Refactoring sem testes não é refactoring — é jogo de azar. Antes de pedir à IA para refatorar qualquer coisa, estabeleça a rede de segurança:

  1. Lock the behavior with tests first. If the code has no tests, write characterization tests before touching anything. Ask AI: "Write tests that characterize the current behavior of this function — including edge cases and expected outputs. Do not suggest improvements yet." These tests are your regression guard.Bloqueie o comportamento com testes primeiro. Se o código não tem testes, escreva testes de caracterização antes de tocar em qualquer coisa. Peça à IA: "Escreva testes que caracterizem o comportamento atual desta função — incluindo edge cases e outputs esperados. Não sugira melhorias ainda." Esses testes são sua guarda contra regressões.
  2. One refactoring at a time. Each AI prompt should apply one named technique. Not "improve this code" — "apply Extract Method to this function". Mixing multiple refactorings in one step makes it impossible to know which change introduced a problem.Um refactoring por vez. Cada prompt de IA deve aplicar uma técnica nomeada. Não "melhore este código" — "aplique Extract Method nesta função". Misturar múltiplos refactorings em um passo torna impossível saber qual mudança introduziu um problema.
  3. Run tests after each step. Green tests confirm behavior is preserved. Red tests — before any other change — mean the refactoring introduced a regression. Revert immediately; don't continue on a broken foundation.Rode os testes após cada passo. Testes verdes confirmam que o comportamento foi preservado. Testes vermelhos — antes de qualquer outra mudança — significam que o refactoring introduziu uma regressão. Reverta imediatamente; não continue sobre uma base quebrada.
  4. Verify the refactoring claim. After AI produces the refactored code, ask: "Identify any place where this refactored version might behave differently from the original — including error handling, edge cases with null or empty values, and exception propagation." This forces a second pass before you accept the output.Verifique a afirmação do refactoring. Após a IA produzir o código refatorado, pergunte: "Identifique qualquer lugar onde esta versão refatorada pode se comportar diferente da original — incluindo tratamento de erros, edge cases com valores null ou vazios e propagação de exceções." Isso força uma segunda passagem antes de aceitar o output.

This tells you where to spend refactoring effort and in what order:Antes de aplicar qualquer técnica, use a IA para produzir um inventário priorizado de smells. Isso indica onde gastar esforço de refactoring e em qual ordem:

"Audit this code for refactoring opportunities. For each smell found: 1. Name the smell (Long Method, Feature Envy, Data Clump, etc.) 2. Point to the specific lines or sections affected 3. Name the refactoring technique that resolves it 4. Estimate the impact on readability and changeability (low/medium/high) Sort results by impact, highest first. "Audite este código em busca de oportunidades de refactoring. Para cada smell encontrado: 1. Nomeie o smell (Long Method, Feature Envy, Data Clump, etc.) 2. Aponte as linhas ou seções específicas afetadas 3. Nomeie a técnica de refactoring que o resolve 4. Extract Method: The Highest-Frequency RefactoringExtract Method: O Refactoring de Maior Frequência

Extract Method is applied more often than any other technique. The trigger: a block of code inside a function that could be described with a name different from the function's name. That block is doing a secondary job and belongs in its own function.Extract Method é aplicado com mais frequência que qualquer outra técnica. O gatilho: um bloco de código dentro de uma função que poderia ser descrito com um nome diferente do nome da função. Esse bloco está fazendo um trabalho secundário e pertence à sua própria função.

// Before: a long function with several embedded jobs function generateMonthlyReport(userId, month, year) { // Fetch user const user = db.users.findOne({ id: userId }); if (!user) throw new UserNotFoundError(userId); // Build date range const startDate = new Date(year, month - 1, 1); const endDate = new Date(year, month, 0, 23, 59, 59); // Fetch transactions const transactions = db.transactions.find({ userId, date: { $gte: startDate, $lte: endDate }, }); // Calculate summary const totalIn = transactions.filter(t => t.type === 'credit').reduce((s, t) => s + t.amount, 0); const totalOut = transactions.filter(t => t.type === 'debit').reduce((s, t) => s + t.amount, 0); const balance = totalIn - totalOut; // Format output return { user: { id: user.id, name: user.name }, period: { month, year }, summary: { totalIn, totalOut, balance }, transactions: transactions.map(t => ({ id: t.id, date: t.date, amount: t.amount, type: t.type })), }; }
// Antes: uma função longa com vários trabalhos embutidos function gerarRelatorioMensal(usuarioId, mes, ano) { // Buscar usuário const usuario = db.usuarios.findOne({ id: usuarioId }); if (!usuario) throw new UsuarioNaoEncontradoError(usuarioId); // Construir intervalo de datas const dataInicio = new Date(ano, mes - 1, 1); const dataFim = new Date(ano, mes, 0, 23, 59, 59); // Buscar transações const transacoes = db.transacoes.find({ usuarioId, data: { $gte: dataInicio, $lte: dataFim }, }); // Calcular resumo const totalEntradas = transacoes.filter(t => t.tipo === 'credito').reduce((s, t) => s + t.valor, 0); const totalSaidas = transacoes.filter(t => t.tipo === 'debito').reduce((s, t) => s + t.valor, 0); const saldo = totalEntradas - totalSaidas; // Formatar saída return { usuario: { id: usuario.id, nome: usuario.nome }, periodo: { mes, ano }, resumo: { totalEntradas, totalSaidas, saldo }, transacoes: transacoes.map(t => ({ id: t.id, data: t.data, valor: t.valor, tipo: t.tipo })), }; }
// Prompt: "Apply Extract Method to this function. Each comment block is a hint // for an extraction. Name each extracted function by its intent, not by what // the comment says. Preserve behavior exactly." // After: function generateMonthlyReport(userId, month, year) { const user = fetchUserOrThrow(userId); const period = buildMonthDateRange(month, year); const transactions = fetchUserTransactionsInPeriod(userId, period); const summary = calculateTransactionSummary(transactions); return formatReportOutput(user, { month, year }, summary, transactions); } function fetchUserOrThrow(userId) { const user = db.users.findOne({ id: userId }); if (!user) throw new UserNotFoundError(userId); return user; } function buildMonthDateRange(month, year) { return { startDate: new Date(year, month - 1, 1), endDate: new Date(year, month, 0, 23, 59, 59), }; } function fetchUserTransactionsInPeriod(userId, { startDate, endDate }) { return db.transactions.find({ userId, date: { $gte: startDate, $lte: endDate } }); } function calculateTransactionSummary(transactions) { const totalIn = transactions.filter(t => t.type === 'credit').reduce((s, t) => s + t.amount, 0); const totalOut = transactions.filter(t => t.type === 'debit').reduce((s, t) => s + t.amount, 0); return { totalIn, totalOut, balance: totalIn - totalOut }; } function formatReportOutput(user, period, summary, transactions) { return { user: { id: user.id, name: user.name }, period, summary, transactions: transactions.map(t => ({ id: t.id, date: t.date, amount: t.amount, type: t.type })), }; }
// Prompt: "Aplique Extract Method nesta função. Cada bloco de comentário é uma // dica para uma extração. Nomeie cada função extraída pela sua intenção, não // pelo que o comentário diz. Preserve o comportamento exatamente." // Depois: function gerarRelatorioMensal(usuarioId, mes, ano) { const usuario = buscarUsuarioOuLancarErro(usuarioId); const periodo = construirIntervaloDatasDoMes(mes, ano); const transacoes = buscarTransacoesUsuarioNoPeriodo(usuarioId, periodo); const resumo = calcularResumoTransacoes(transacoes); return formatarSaidaRelatorio(usuario, { mes, ano }, resumo, transacoes); } function buscarUsuarioOuLancarErro(usuarioId) { const usuario = db.usuarios.findOne({ id: usuarioId }); if (!usuario) throw new UsuarioNaoEncontradoError(usuarioId); return usuario; } function construirIntervaloDatasDoMes(mes, ano) { return { dataInicio: new Date(ano, mes - 1, 1), dataFim: new Date(ano, mes, 0, 23, 59, 59), }; } function buscarTransacoesUsuarioNoPeriodo(usuarioId, { dataInicio, dataFim }) { return db.transacoes.find({ usuarioId, data: { $gte: dataInicio, $lte: dataFim } }); } function calcularResumoTransacoes(transacoes) { const totalEntradas = transacoes.filter(t => t.tipo === 'credito').reduce((s, t) => s + t.valor, 0); const totalSaidas = transacoes.filter(t => t.tipo === 'debito').reduce((s, t) => s + t.valor, 0); return { totalEntradas, totalSaidas, saldo: totalEntradas - totalSaidas }; } function formatarSaidaRelatorio(usuario, periodo, resumo, transacoes) { return { usuario: { id: usuario.id, nome: usuario.nome }, periodo, resumo, transacoes: transacoes.map(t => ({ id: t.id, data: t.data, valor: t.valor, tipo: t.tipo })), }; }

Introduce Parameter Object: Eliminating Data ClumpsIntroduce Parameter Object: Eliminando Data Clumps

Data Clump is the smell of parameters that always travel together. When you see the same three or four parameters in multiple function signatures, they belong in a named object. AI identifies clumps and generates the object and all the callers in one step:Data Clump é o smell de parâmetros que sempre viajam juntos. Quando você vê os mesmos três ou quatro parâmetros em múltiplas assinaturas de função, eles pertencem a um objeto nomeado. A IA identifica os clumps e gera o objeto e todos os chamadores em um passo:

// Smell: the same parameter group appears in every function function searchFlights(origin, destination, departureDate, returnDate) { ... } function estimateFlightCost(origin, destination, departureDate, returnDate) { ... } function bookFlight(origin, destination, departureDate, returnDate, passengerId) { ... } function findAlternativeFlights(origin, destination, departureDate, returnDate) { ... } // Prompt: "Apply Introduce Parameter Object. Identify the data clump, // create a named value object for it, and update all function signatures. // The object should validate its own invariants in the constructor." class FlightRoute { constructor({ origin, destination, departureDate, returnDate }) { if (!origin || !destination) throw new Error('Origin and destination are required'); if (returnDate && returnDate < departureDate) throw new Error('Return must be after departure'); this.origin = origin; this.destination = destination; this.departureDate = departureDate; this.returnDate = returnDate; } get isRoundTrip() { return !!this.returnDate; } } // Updated signatures — callers become readable function searchFlights(route: FlightRoute) { ... } function estimateFlightCost(route: FlightRoute) { ... } function bookFlight(route: FlightRoute, passengerId: string) { ... } function findAlternativeFlights(route: FlightRoute) { ... }
// Smell: o mesmo grupo de parâmetros aparece em toda função function buscarVoos(origem, destino, dataPartida, dataRetorno) { ... } function estimarCustoVoo(origem, destino, dataPartida, dataRetorno) { ... } function reservarVoo(origem, destino, dataPartida, dataRetorno, passageiroId) { ... } function encontrarVoosAlternativos(origem, destino, dataPartida, dataRetorno) { ... } // Prompt: "Aplique Introduce Parameter Object. Identifique o data clump, // crie um objeto de valor nomeado para ele e atualize todas as assinaturas // de função. O objeto deve validar seus próprios invariantes no construtor." class RotaVoo { constructor({ origem, destino, dataPartida, dataRetorno }) { if (!origem || !destino) throw new Error('Origem e destino são obrigatórios'); if (dataRetorno && dataRetorno < dataPartida) throw new Error('Retorno deve ser após a partida'); this.origem = origem; this.destino = destino; this.dataPartida = dataPartida; this.dataRetorno = dataRetorno; } get ehIdaEVolta() { return !!this.dataRetorno; } } // Assinaturas atualizadas — chamadores ficam legíveis function buscarVoos(rota: RotaVoo) { ... } function estimarCustoVoo(rota: RotaVoo) { ... } function reservarVoo(rota: RotaVoo, passageiroId: string) { ... } function encontrarVoosAlternativos(rota: RotaVoo) { ... }

Replace Conditional with PolymorphismReplace Conditional with Polymorphism

When the same switch or type-checking conditional appears in multiple methods of the same class, it's a sign that the type should drive behavior through inheritance or composition instead of branching. This refactoring is the bridge between a code smell and a design pattern (Strategy or State):Quando o mesmo switch ou condicional de verificação de tipo aparece em múltiplos métodos da mesma classe, é sinal de que o tipo deve conduzir o comportamento por herança ou composição em vez de ramificação. Este refactoring é a ponte entre um code smell e um design pattern (Strategy ou State):

// Smell: repeated type dispatch across multiple methods class Shipping { calculateCost(order) { switch (order.shippingType) { case 'standard': return order.weight * 2.5; case 'express': return order.weight * 5.0 + 10; case 'overnight': return order.weight * 8.0 + 25; } } estimateDeliveryDays(order) { switch (order.shippingType) { case 'standard': return 7; case 'express': return 3; case 'overnight': return 1; } } getCarrierCode(order) { switch (order.shippingType) { case 'standard': return 'STD-01'; case 'express': return 'EXP-02'; case 'overnight': return 'OVN-03'; } } } // Prompt: "Replace the repeated type conditionals with polymorphism. // Each shipping type should be a class that encapsulates its own rules. // The Shipping class should delegate to the appropriate type." class StandardShipping { calculateCost(order) { return order.weight * 2.5; } estimateDeliveryDays() { return 7; } get carrierCode() { return 'STD-01'; } } class ExpressShipping { calculateCost(order) { return order.weight * 5.0 + 10; } estimateDeliveryDays() { return 3; } get carrierCode() { return 'EXP-02'; } } class OvernightShipping { calculateCost(order) { return order.weight * 8.0 + 25; } estimateDeliveryDays() { return 1; } get carrierCode() { return 'OVN-03'; } } class Shipping { private static types = { standard: new StandardShipping(), express: new ExpressShipping(), overnight: new OvernightShipping(), }; static for(type) { const shipping = Shipping.types[type]; if (!shipping) throw new UnsupportedShippingTypeError(type); return shipping; } } // Usage: const shipping = Shipping.for(order.shippingType); const cost = shipping.calculateCost(order); const days = shipping.estimateDeliveryDays();
// Smell: despacho de tipo repetido em múltiplos métodos class Envio { calcularCusto(pedido) { switch (pedido.tipoEnvio) { case 'padrao': return pedido.peso * 2.5; case 'expresso': return pedido.peso * 5.0 + 10; case 'noturno': return pedido.peso * 8.0 + 25; } } estimarDiasEntrega(pedido) { switch (pedido.tipoEnvio) { case 'padrao': return 7; case 'expresso': return 3; case 'noturno': return 1; } } obterCodigoTransportadora(pedido) { switch (pedido.tipoEnvio) { case 'padrao': return 'PAD-01'; case 'expresso': return 'EXP-02'; case 'noturno': return 'NOT-03'; } } } // Prompt: "Substitua os condicionais de tipo repetidos por polimorfismo. // Cada tipo de envio deve ser uma classe que encapsula suas próprias regras. // A classe Envio deve delegar ao tipo apropriado." class EnvioPadrao { calcularCusto(pedido) { return pedido.peso * 2.5; } estimarDiasEntrega() { return 7; } get codigoTransportadora() { return 'PAD-01'; } } class EnvioExpresso { calcularCusto(pedido) { return pedido.peso * 5.0 + 10; } estimarDiasEntrega() { return 3; } get codigoTransportadora() { return 'EXP-02'; } } class EnvioNoturno { calcularCusto(pedido) { return pedido.peso * 8.0 + 25; } estimarDiasEntrega() { return 1; } get codigoTransportadora() { return 'NOT-03'; } } class Envio { private static tipos = { padrao: new EnvioPadrao(), expresso: new EnvioExpresso(), noturno: new EnvioNoturno(), }; static para(tipo) { const envio = Envio.tipos[tipo]; if (!envio) throw new TipoEnvioNaoSuportadoError(tipo); return envio; } } // Uso: const envio = Envio.para(pedido.tipoEnvio); const custo = envio.calcularCusto(pedido); const dias = envio.estimarDiasEntrega();

Extract Class: When a Class Does Too MuchExtract Class: Quando uma Classe Faz Demais

Extract Method addresses long functions. Extract Class addresses the next level: a class whose fields and methods naturally cluster into two or more cohesive groups. The tell: if you can describe parts of a class independently, those parts belong in separate classes.Extract Method trata funções longas. Extract Class trata o próximo nível: uma classe cujos campos e métodos se agrupam naturalmente em dois ou mais grupos coesos. O sinal: se você consegue descrever partes de uma classe de forma independente, essas partes pertencem a classes separadas.

// Smell: User class manages both identity and address concerns class User { // Identity fields id: string; email: string; passwordHash: string; lastLoginAt: Date; // Address fields street: string; city: string; state: string; postalCode: string; country: string; // Identity methods verifyPassword(plain) { ... } updateEmail(newEmail) { ... } // Address methods formatFullAddress() { return `${this.street}, ${this.city} - ${this.state}`; } isInternational() { return this.country !== 'BR'; } toShippingLabel() { ... } } // Prompt: "Apply Extract Class. Move Method: Fixing Feature EnvyMove Method: Corrigindo Feature Envy

Feature Envy is the smell of a method that uses more data from another class than from its own. The method is in the wrong class. Moving it is often the simplest refactoring with the highest readability payoff:Feature Envy é o smell de um método que usa mais dados de outra classe do que da sua própria. O método está na classe errada. Movê-lo é frequentemente o refactoring mais simples com o maior retorno de legibilidade:

// Smell: OrderService.calculateShipping touches only Order fields class OrderService { calculateShipping(order) { // This method only knows about Order. It belongs in Order. const baseRate = order.weight * 2.5; const fragile = order.isFragile ? baseRate * 0.20 : 0; const insurance = order.totalValue > 500 ? order.totalValue * 0.01 : 0; return baseRate + fragile + insurance; } } // Prompt: "Apply Move Method. Identify which class this method belongs to // based on the data it accesses. Move it there. Update the caller." class Order { // ...existing fields... calculateShipping() { const baseRate = this.weight * 2.5; const fragile = this.isFragile ? baseRate * 0.20 : 0; const insurance = this.totalValue > 500 ? this.totalValue * 0.01 : 0; return baseRate + fragile + insurance; } } // OrderService no longer needs the method: class OrderService { processOrder(order) { const shippingCost = order.calculateShipping(); // natural // ... } }
// Smell: PedidoService.calcularFrete acessa apenas campos de Pedido class PedidoService { calcularFrete(pedido) { // Este método só conhece Pedido. Ele pertence a Pedido. const taxaBase = pedido.peso * 2.5; const fragil = pedido.eFragil ? taxaBase * 0.20 : 0; const seguro = pedido.valorTotal > 500 ? pedido.valorTotal * 0.01 : 0; return taxaBase + fragil + seguro; } } // Prompt: "Aplique Move Method. Identifique a qual classe este método pertence // com base nos dados que acessa. Mova-o para lá. Atualize o chamador." class Pedido { // ...campos existentes... calcularFrete() { const taxaBase = this.peso * 2.5; const fragil = this.eFragil ? taxaBase * 0.20 : 0; const seguro = this.valorTotal > 500 ? this.valorTotal * 0.01 : 0; return taxaBase + fragil + seguro; } } // PedidoService não precisa mais do método: class PedidoService { processarPedido(pedido) { const custoFrete = pedido.calcularFrete(); // natural // ... } }

The Characterization Test PromptO Prompt de Teste de Caracterização

When refactoring code that has no tests, the first step is always generating characterization tests — tests that document current behavior, not intended behavior. These lock what the code does before you change how it does it:Quando refatorando código sem testes, o primeiro passo é sempre gerar testes de caracterização — testes que documentam o comportamento atual, não o comportamento pretendido. Eles travam o que o código faz antes de mudar como ele faz:

"Write characterization tests for this function. The goal is NOT to test that the behavior is correct — it is to document and lock the current behavior so that any refactoring that changes the output is caught immediately. For each test: - Use a descriptive name that states WHAT the function returns for WHICH input - Cover: typical inputs, boundary values, empty/null inputs, error conditions - Do NOT improve or fix the behavior — test it as-is, even if it seems wrong After writing the tests, list any behaviors that seem suspicious or incorrect so I can decide whether to fix them separately before refactoring."
"Escreva testes de caracterização para esta função. O objetivo NÃO é testar que o comportamento é correto — é documentar e travar o comportamento atual para que qualquer refactoring que mude o output seja capturado imediatamente. Para cada teste: - Use um nome descritivo que diga O QUE a função retorna para QUAL entrada - Cubra: entradas típicas, valores de fronteira, entradas vazias/null, condições de erro - NÃO melhore nem corrija o comportamento — teste como está, mesmo que pareça errado Após escrever os testes, liste qualquer comportamento que pareça suspeito ou incorreto para que eu possa decidir se devo corrigi-lo separadamente antes do refactoring."

The Behavior-Preservation CheckA Verificação de Preservação de Comportamento

After AI generates a refactored version, always run this prompt before accepting:Após a IA gerar uma versão refatorada, sempre execute este prompt antes de aceitar:

"Compare the original and refactored versions carefully. List every case where they might behave differently: 1. Return values: are all return paths equivalent? 2. Exceptions: does the refactored version throw in any case the original doesn't, or swallow any exception the original propagates? 3. Side effects: any difference in what gets written, logged, or emitted? 4. Null/undefined handling: does either version handle missing values differently? 5. Short-circuit evaluation: does any extracted function change when evaluation stops? 6. Mutation: does any extraction change whether an object is mutated in place? For each difference found, state whether it is an intentional improvement or an unintentional behavior change."
"Compare as versões original e refatorada cuidadosamente. Liste cada caso onde podem se comportar diferente: 1. Valores de retorno: todos os caminhos de retorno são equivalentes? 2. Exceções: a versão refatorada lança em algum caso que a original não lança, ou engole alguma exceção que a original propaga? 3. Efeitos colaterais: alguma diferença no que é escrito, logado ou emitido? 4. Tratamento de null/undefined: alguma versão trata valores ausentes diferente? 5. Avaliação em curto-circuito: alguma função extraída muda quando a avaliação para? 6. Mutação: alguma extração muda se um objeto é mutado no local? Para cada diferença encontrada, diga se é uma melhoria intencional ou uma mudança de comportamento não intencional."

Where AI Refactoring Goes WrongOnde o Refactoring com IA Dá Errado

Silent behavior changes. The most dangerous AI refactoring mistake is changing behavior while claiming to preserve it. Common culprits: reordering operations that have side effects, changing error propagation in extracted functions, losing a null guard that was buried in a conditional. The behavior-preservation check prompt catches most of these, but it requires tests to confirm.Mudanças de comportamento silenciosas. O erro de refactoring mais perigoso da IA é mudar comportamento alegando preservá-lo. Culpados comuns: reordenar operações com efeitos colaterais, mudar propagação de erros em funções extraídas, perder um guard de null que estava enterrado em um condicional. O prompt de verificação de preservação de comportamento captura a maioria, mas exige testes para confirmar.

Over-extraction. AI tends to extract aggressively. A three-line block becomes a named function. A two-step calculation becomes two separate functions. The result is code where following the logic requires jumping between ten short functions instead of reading thirty sequential lines. Extract when the extracted unit has a name that adds information. Don't extract just because a block is separable.Extração excessiva. A IA tende a extrair agressivamente. Um bloco de três linhas vira uma função nomeada. Um cálculo de duas etapas vira duas funções separadas. O resultado é código onde seguir a lógica exige saltar entre dez funções curtas em vez de ler trinta linhas sequenciais. Extraia quando a unidade extraída tem um nome que adiciona informação. Não extraia só porque um bloco é separável.

Mixing refactoring with bug fixes. AI will occasionally notice what looks like a bug and fix it silently while refactoring. This is dangerous: the "bug" might be intentional behavior, and the fix changes semantics while you're focused on structure. Always ask: "Did you fix anything that wasn't a structural change? If so, list it explicitly."Misturar refactoring com correção de bugs. A IA ocasionalmente nota o que parece um bug e o corrige silenciosamente durante o refactoring. Isso é perigoso: o "bug" pode ser comportamento intencional, e a correção muda a semântica enquanto você está focado na estrutura. Sempre pergunte: "Você corrigiu algo que não era uma mudança estrutural? Se sim, liste explicitamente."

The refactoring contract: Tell AI explicitly: "This is a structural refactoring only. Do not fix bugs, improve algorithms, add error handling, or change behavior — even if you see an opportunity. Structural changes only. Flag anything that looks like a bug separately." This constraint is the difference between a refactoring session and a combined refactoring + feature change that's impossible to review safely.O contrato de refactoring: Diga à IA explicitamente: "Este é um refactoring apenas estrutural. Não corrija bugs, não melhore algoritmos, não adicione tratamento de erros e não mude comportamento — mesmo que veja uma oportunidade. Apenas mudanças estruturais. Sinalize separadamente qualquer coisa que pareça um bug." Esta restrição é a diferença entre uma sessão de refactoring e uma mudança combinada de refactoring + feature que é impossível de revisar com segurança.

Refactoring Legacy Code: A Practical SequenceRefactoring de Código Legado: Uma Sequência Prática

Legacy code is often the most valuable candidate for refactoring and the riskiest place to apply it. This sequence minimizes risk when AI-assisted refactoring hits a 500-line class with no tests and unclear ownership:Código legado é frequentemente o candidato mais valioso para refactoring e o lugar mais arriscado para aplicá-lo. Esta sequência minimiza o risco quando o refactoring com IA encontra uma classe de 500 linhas sem testes e propriedade pouco clara:

  1. Understand before touching. Prompt: "Explain what this code does, section by section. List every input, output, side effect, and external dependency. Do not suggest changes yet."Entenda antes de tocar. Prompt: "Explique o que este código faz, seção por seção. Liste cada entrada, saída, efeito colateral e dependência externa. Não sugira mudanças ainda."
  2. Write characterization tests. Cover the behavior you understand. Accept that you won't cover what you don't understand yet — that coverage comes after step 3.Escreva testes de caracterização. Cubra o comportamento que você entende. Aceite que não cobrirá o que ainda não entende — essa cobertura vem após o passo 3.
  3. Apply Rename first. Better names cost nothing and make everything else clearer. Ask AI to rename every unclear variable, method, and class before doing any structural change.Aplique Rename primeiro. Nomes melhores não custam nada e tornam tudo mais claro. Peça à IA para renomear cada variável, método e classe pouco claros antes de fazer qualquer mudança estrutural.
  4. Apply Extract Method for comment-demarcated blocks. Any comment that says "do X" is a hint for an extraction named X. This makes the structure explicit without changing behavior.Aplique Extract Method para blocos demarcados por comentários. Qualquer comentário que diz "fazer X" é uma dica para uma extração chamada X. Isso torna a estrutura explícita sem mudar o comportamento.
  5. Apply Extract Class when clusters emerge. After extraction, field-and-method clusters become visible. Move related things together.Aplique Extract Class quando clusters emergirem. Após a extração, clusters de campos e métodos ficam visíveis. Mova coisas relacionadas juntas.
  6. Replace conditionals with polymorphism last. This is the deepest structural change. Apply it only after the code is well-named and well-extracted, so the conditional structure is easy to see and reason about.Substitua condicionais por polimorfismo por último. Esta é a mudança estrutural mais profunda. Aplique apenas após o código estar bem nomeado e bem extraído, para que a estrutura condicional seja fácil de ver e raciocinar.

The compounding effect: Refactoring creates a virtuous cycle with AI. Better-structured code produces better AI suggestions — the AI reasons about a focused, named function far more accurately than about a 200-line entangled block. Better AI suggestions produce better refactoring proposals. The investment in structure compounds: each refactoring session leaves the codebase in better shape for the next one, and each session costs less because the code is easier to reason about.O efeito composto: Refactoring cria um ciclo virtuoso com a IA. Código melhor estruturado produz melhores sugestões de IA — ela raciocina sobre uma função focada e nomeada com muito mais precisão do que sobre um bloco entrelaçado de 200 linhas. Melhores sugestões de IA produzem melhores propostas de refactoring. O investimento em estrutura gera juros compostos: cada sessão de refactoring deixa o codebase em melhor forma para a próxima, e cada sessão custa menos porque o código é mais fácil de raciocinar.

Key TakeawaysPontos Principais

  • Refactoring is structural change without behavior change. Establish tests before touching anything. Run them after every single AI-applied technique. One technique per prompt, one prompt per commit.Refactoring é mudança estrutural sem mudança de comportamento. Estabeleça testes antes de tocar em qualquer coisa. Rode-os após cada técnica aplicada pela IA. Uma técnica por prompt, um prompt por commit.
  • Start with the smell audit prompt: inventory all smells, sort by impact, review the plan before generating refactored code. You own the prioritization — don't outsource it.Comece com o prompt de auditoria de smells: inventarie todos os smells, ordene por impacto, revise o plano antes de gerar código refatorado. Você é dono da priorização — não a terceirize.
  • Extract Method is the most frequently applied technique. Any comment block that says "do X" is a hint for a function named X. Use it to make structure visible without changing behavior.Extract Method é a técnica mais aplicada com frequência. Qualquer bloco de comentário que diz "fazer X" é uma dica para uma função chamada X. Use-o para tornar a estrutura visível sem mudar o comportamento.
  • Introduce Parameter Object when the same 3+ parameters appear together across multiple functions. The object validates its own invariants and gives the clump a name.Introduce Parameter Object quando os mesmos 3+ parâmetros aparecem juntos em múltiplas funções. O objeto valida seus próprios invariantes e dá um nome ao clump.
  • Replace Conditional with Polymorphism when the same type dispatch appears in multiple methods. Each type becomes a class; the dispatcher becomes a map or registry.Replace Conditional with Polymorphism quando o mesmo despacho de tipo aparece em múltiplos métodos. Cada tipo vira uma classe; o dispatcher vira um mapa ou registry.
  • Always run the behavior-preservation check after AI refactoring: compare return paths, exception handling, side effects, null behavior, and mutations between the original and refactored version.Sempre execute a verificação de preservação de comportamento após refactoring com IA: compare caminhos de retorno, tratamento de exceções, efeitos colaterais, comportamento com null e mutações entre a versão original e a refatorada.
  • Enforce the refactoring contract: structural changes only, no bug fixes, no behavior improvements, no new features. If AI notices a bug, it goes in a separate ticket — not in the same refactoring commit.Aplique o contrato de refactoring: apenas mudanças estruturais, sem correção de bugs, sem melhorias de comportamento, sem novas features. Se a IA notar um bug, vai para um ticket separado — não no mesmo commit de refactoring.
